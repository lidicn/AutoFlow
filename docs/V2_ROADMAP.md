### Git 工作流

```
main（稳定）← develop（集成）← feature/*（功能分支）
     ↑              ↑
   发布标签      每日合并
```

- **每个功能一个分支**：`feature/xxx`，开发完成后 PR 到 develop
- **每日集成**：PM 协调，reviewer 审查后合并到 develop
- **每周发布**：develop 合并到 main，打标签 `v2.x.x`
- **代码回滚**：`git revert` 或 `git reset --hard <commit>`，所有提交都有记录

## 八、与主版本的关系

```
主版本 autoflow（稳定）          V2 实验版（创新）
      │                              │
      ├── v1.5.x 开发迭代 ──────────→│ 吸收 + 实验增强
      ├── v1.6.0 稳定版 ───────────→│ 基线对齐
      ├── v1.6.x 经验复用 ─────────→│ 吸收 + 实验增强
      │                              │
      │  ← 优秀成果合并 ─────────────┤
      │                              │
      └── v2.x.x 竞技场 ────────────→│ 先行验证
```

**规则**：
1. V2 从主版本吸收稳定功能，加入实验性增强
2. V2 验证成功的功能，反馈给主版本
3. V2 可以大胆尝试，崩了只影响实验环境
4. 主版本保持稳定，不轻易引入未验证功能

## 九、测试策略

### 9.1 开发自验（每个提交必做）
```
1. python -m py_compile 所有修改的 .py 文件
2. 提交后部署到 NAS（:8002）
3. curl 验证核心接口
4. 检查容器日志无报错
```

### 9.2 集中测试（每周一次）
```
1. tester 执行全功能回归
2. 返回结果 + 证据
3. backend-dev 修复 P0/P1 bug
4. 修复后自验，必要时再开一轮回归
```

### 9.3 阶段结束回归（每个 Phase 结束）
```
1. 全功能回归测试
2. 性能测试（响应时间、token 消耗）
3. 安全测试（授权越界、吊销、频率限制）
4. 发布稳定版
```
