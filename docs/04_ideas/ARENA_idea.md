# 竞技场模式 — 想法草稿

> **状态**：想法阶段，暂不纳入开发计划
> **创建时间**：2026-09-05
> **来源**：dw 与大佬闲聊时的异想天开

---

## 一、核心想法

授权一批真实设备，让多个 Agent 通过 AutoFlow Pro 版往「竞技场」编写 flow（统一从 inject 节点开始）。通过竞技场获得：
- 经验数据（Agent 的编写轨迹、成功/失败模式）
- DSL bug（真实环境暴露的边界 case）
- 优质 flow（通过实际运行验证的 flow）

交卷时统一验收：一次触发全部 flow，通过 debug 或物理设备验证。

---

## 二、核心价值

| 收获 | 说明 |
|------|------|
| **经验数据** | 多个 Agent 的编写轨迹、成功/失败模式，为经验复用提供素材 |
| **DSL bug** | 真实环境暴露 DSL 的边界 case 和编译失败案例 |
| **优质 flow** | 通过实际运行验证的 flow，可直接入模板库 |
| **Agent 能力对比** | 不同 Agent 在同一环境下的表现数据 |

本质：把「经验复用」从**被动收集**变成**主动获取**。

---

## 三、三层竞技场架构

直接用真实设备有风险，建议分层：

```
┌─────────────────────────────────────────────┐
│  L3 实战层：真实设备（用户授权，严格配额）    │
│  - 验证真实物理交互                          │
│  - 操作频率限制、危险操作拦截                │
│  - 验收后自动恢复设备状态                    │
├─────────────────────────────────────────────┤
│  L2 仿真层：真实设备只读/限频                │
│  - 验证 entity_id 真实性、服务调用格式       │
│  - 不实际改变设备状态                        │
├─────────────────────────────────────────────┤
│  L1 沙盒层：vhass 虚拟设备（完全隔离）       │
│  - Agent 随便折腾，无任何风险                │
│  - 快速迭代 DSL 和 flow 逻辑                │
│  - 90% 的编写和调试在这里完成                │
└─────────────────────────────────────────────┘
```

**晋级机制**：Agent 从 L1 开始，通过验收后晋级 L2/L3。

---

## 四、统一规范（竞技场规则）

```
Flow 命名：arena_<agent_id>_<flow_name>
起始节点：必须是 inject，id 前缀 af_arena_inject_
预期声明：每个 flow 必须提交 postconditions（触发后哪些设备应该是什么状态）
隔离边界：Agent 只能修改自己 arena_ 前缀的 flow
```

---

## 五、自动化验收流程

```
1. 快照：记录所有授权设备的当前状态
2. 触发：通过 NR Admin API 批量触发所有 af_arena_inject_ 节点
3. 等待：固定 N 秒（或等待所有 flow 执行完成）
4. 采集：读取设备最终状态
5. 对比：预期 postconditions vs 实际状态
6. 报告：每个 flow 的通过率、响应时间、副作用
7. 回滚：恢复设备到快照状态
```

---

## 六、安全闸门（必须有）

- **设备白名单**：只有用户明确授权的设备可操作
- **频率限制**：每个设备每分钟最多 N 次状态变更
- **危险操作拦截**：删除其他 Agent 的 flow、覆盖非 arena_ 前缀的 tab → 拒绝
- **自动熔断**：某设备 1 分钟内被操作超过阈值 → 暂停所有 Agent 对该设备的操作
- **验收后清理**：自动删除测试 flow，恢复设备状态

---

## 七、经验提取管道

```
竞技场运行数据
    │
    ├─ 编译失败的 DSL → 错误知识库（"这种写法会失败"）
    ├─ 运行失败的 flow → 常见陷阱库（"这种场景有坑"）
    ├─ 通过验收的 flow → 模板库（"这种写法靠谱"）
    └─ Agent 操作轨迹 → 最佳实践（"高效 Agent 的编写顺序"）
```

---

## 八、改进建议

### 1. 挑战任务机制

不是让 Agent 随便写，而是给**明确的任务**：

> 挑战 001：有人按门铃时，客厅灯亮起 30 秒，并发送通知
> 挑战 002：晚上 11 点后，卧室温度低于 20 度时自动开空调
> 挑战 003：检测到漏水时，关闭水阀并推送紧急通知

每个挑战有**明确的验收标准**，Agent 交卷后自动评分。

### 2. 排行榜 + 复用机制

- Agent 通过率、flow 质量评分排行
- 优质 flow 被其他 Agent 收藏/复用的次数
- 形成「社区驱动」的模板库

### 3. 渐进式开放

```
v1.6：L1 沙盒竞技场（vhass 虚拟设备，单 Agent）
v1.7：多 Agent 支持 + 挑战任务 + 自动验收
v1.8：L2 仿真层（真实设备只读）
v2.0：L3 实战层 + 经验提取管道 + 排行榜
```

## 九、待讨论问题

1. 竞技场是独立 NR 实例，还是主 NR 的一个隔离 tab？
2. 真实设备授权的粒度：按设备？按域？按操作类型？
3. 多 Agent 同时写同一个 NR 实例的冲突如何解决？
4. 验收标准如何定义？纯状态对比？还是包含响应时间、副作用？
5. 经验提取是人工审核还是自动入库？
6. 竞技场数据是否公开？还是仅本地使用？

---

## 十、结论

**可行，且是高价值功能。** 它解决了经验复用的核心难题——**数据从哪来**。

但不建议一上来就用真实设备，应该：
1. 先做 L1 沙盒层（vhass），验证流程
2. 增加挑战任务和自动验收
3. 成熟后再开放真实设备

可作为 **v2.0 的核心功能**，当前先把 v1.5.x 的 Pro 版基础打牢。
