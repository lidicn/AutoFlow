## 一、目标与定位

### 1.1 竞技场的核心目标是什么？
- [x] 收集经验数据（失败案例、DSL bug、优质 flow）
- [x] 评估不同 Agent 的能力（排行榜、对比）
- [ ] 让用户娱乐化地使用 AutoFlow（游戏化）
- [x] 验证 AutoFlow Pro 的稳定性和安全性
- [ ] 其他

**理由**：竞技场的核心价值是"主动获取经验数据"。现有经验收集是被动的（用户用了才有），竞技场可以主动制造大量高质量的成功/失败案例。排行榜是副产品，用于激励 Agent 开发者参与。游戏化不是重点，极客用户更看重技术价值。

### 1.2 竞技场的主要用户是谁？
- [x] Agent 开发者（测试自己的 Agent）
- [ ] 普通用户（看排行榜、用优质 flow）
- [x] AutoFlow 开发者（收集 bug 和经验）
- [ ] 其他

**理由**：初期主要是 Agent 开发者和 AutoFlow 开发者自己用。普通用户的价值在后期（经验市场）才会体现。

### 1.3 竞技场与现有 Pro 版的关系？
- [x] 独立模块，Pro 用户可选开启
- [ ] Pro 版的内置功能，默认开启
- [ ] 独立部署，与生产环境完全隔离
- [ ] 其他

**理由**：竞技场有安全风险，不应该默认开启。但复用 Pro 版的 API Key、经验收集、安全闸门等基础设施，不需要完全独立部署。用户在 WebUI 开启竞技场后，系统自动创建独立的 NR 实例和虚拟设备。

## 二、架构与隔离

### 2.1 竞技场的 NR 实例如何部署？
- [x] 独立 Docker 容器，与生产 NR 完全隔离
- [ ] 复用生产 NR，但使用独立 tab（命名空间隔离）
- [ ] 云端共享 NR 实例，多用户共用
- [ ] 其他

**理由**：安全第一。竞技场的 Agent 可能编写危险 flow，必须与生产完全隔离。独立 Docker 容器是最可靠的隔离方式。可以用 docker-compose 一键启动 arena-nr + arena-ha(vhass)。

### 2.2 设备来源有哪些层级？
- [x] L1：vhass 虚拟设备（完全模拟，无真实影响）
- [x] L2：真实设备只读/限频（不影响生产，但能读真实状态）
- [x] L3：用户授权的真实设备（可写，但严格配额）
- [ ] 其他

**理由**：三层渐进式开放。MVP 只做 L1，L2/L3 在 v2.1+ 逐步开放。L1 足够收集大部分经验数据。

### 2.3 如何防止竞技场影响生产环境？
- [x] 完全独立的 NR + HA 实例
- [x] 网络隔离（不同 VLAN / Docker 网络）
- [x] 设备白名单（只有授权设备可被操作）
- [x] 频率限制（单位时间内最多操作 N 次）
- [x] 操作审计（所有操作可追溯）
- [ ] 其他

**理由**：纵深防御。独立实例是基础，网络隔离是保障，白名单和频率限制是兜底，审计是事后追溯。全部都要有。

### 2.4 多个 Agent 同时编写 flow 时如何隔离？
- [x] 每个 Agent 独立 tab（当前模式）
- [ ] 每个 Agent 独立 NR 实例
- [ ] 共享 tab，但节点 ID 加 Agent 前缀
- [ ] 其他

**理由**：复用现有 tab 组织模式。每个 Agent 一个 tab，互不干扰。独立 NR 实例太重，MVP 阶段不需要。

## 三、挑战任务设计

### 3.1 挑战任务如何定义？
- [x] 预定义任务库（官方维护，按难度分级）
- [ ] 用户自定义任务（用户创建挑战）
- [x] 两者都支持
- [ ] 其他

**理由**：MVP 只做预定义任务库，保证质量。用户自定义在 v2.1+ 开放，需要审核机制。

### 3.2 任务难度如何分级？
- [x] 简单（单 trigger 单 action，如"开灯"）
- [x] 中等（多条件、多 action，如"温度高且有人时开空调"）
- [x] 困难（复杂逻辑、错误处理、多设备联动）
- [x] 地狱（边界情况、并发、状态机）
- [ ] 其他

**理由**：四级难度覆盖从入门到专家。简单任务用于新手 Agent 验证基础能力，地狱任务用于挖掘 DSL 编译器和 Agent 的边界。

### 3.3 任务的验收标准是什么？
- [x] 触发 inject 后，HA 实体状态符合预期
- [x] flow 能正确编译并部署
- [x] flow 不包含危险操作（如删除所有设备）
- [x] token 消耗在合理范围内
- [ ] flow 可维护性（节点命名、注释）
- [ ] 其他

**理由**：功能正确性是核心（触发后状态正确）。编译部署是基础。危险操作检测是安全底线。token 效率是 Pro 版的核心卖点。可维护性太主观，MVP 不做。

### 3.4 任务是否有时间限制？
- [ ] 有，每个任务限时 N 分钟
- [x] 没有，Agent 可以慢慢写
- [ ] 分阶段，简单任务限时，困难任务不限时
- [ ] 其他

**理由**：MVP 不做时间限制。Agent 的速度差异很大，时间限制会增加复杂度。速度可以作为评分维度，但不作为硬性限制。

## 四、Agent 接入

### 4.1 Agent 如何接入竞技场？
- [x] 通过 Pro 版 API Key（与现有 Pro 一致）
- [ ] 独立的竞技场 API Key（与生产隔离）
- [ ] MCP 接口（Agent 通过 MCP 调用）
- [ ] WebSocket 实时接口（更高效）
- [ ] 其他

**理由**：复用现有 Pro 版 API Key 体系，降低接入成本。Agent 已经有 Pro 版的接入代码，只需要把 gateway_url 指向竞技场实例即可。竞技场的 API Key 有特殊标记（arena=true），只能访问竞技场接口。

### 4.2 Agent 如何知道当前挑战任务？
- [x] API 查询任务列表和详情
- [ ] 任务描述通过 prompt 注入给 Agent
- [ ] WebUI 展示任务，用户复制给 Agent
- [ ] 其他

**理由**：API 查询最灵活。Agent 可以先 GET /api/arena/challenges 查看可用任务，选择后 GET /api/arena/challenges/{id} 获取详情（含验收标准），然后编写 flow 提交。

### 4.3 Agent 提交 flow 的方式？
- [x] propose-dsl（DSL 优先，与现有一致）
- [ ] deploy-raw（raw JSON，逃生舱）
- [x] 两者都支持
- [ ] 其他

**理由**：与 Pro 版一致。DSL 优先，raw 作为逃生舱。竞技场的 propose-dsl 会自动关联当前挑战任务 ID。

### 4.4 是否允许 Agent 多次尝试？
- [x] 允许，每个任务最多 N 次尝试
- [ ] 不限次数，但每次尝试消耗 token
- [ ] 只允许一次提交
- [ ] 其他

**理由**：允许有限次尝试（如 5 次），鼓励 Agent 从失败中学习。尝试次数本身就是评分维度（越少分越高）。不限次会导致刷分和资源浪费。

## 五、验收与评分

### 5.1 验收如何执行？
- [x] 自动触发 inject 节点，观测 HA 状态变化
- [x] 静态分析 flow 结构（节点类型、连接关系）
- [ ] 人工审核（复杂任务需要人判断）
- [ ] 其他

**理由**：MVP 全自动验收。触发 inject 后等待 N 秒，检查 HA 实体状态是否符合预期。静态分析用于检测危险操作。人工审核在 v2.1+ 作为可选机制。

### 5.2 评分维度有哪些？
- [x] 功能正确性（是否完成任务）
- [x] token 效率（消耗越少分越高）
- [x] 尝试次数（越少分越高）
- [ ] flow 质量（可维护性、注释）
- [ ] 速度（完成时间越短分越高）
- [ ] 创新性（非显而易见的解法）
- [ ] 其他

**理由**：MVP 三个维度：正确性（一票否决）、token 效率（Pro 核心卖点）、尝试次数（学习能力）。速度和创新性太主观，后期再加。

### 5.3 评分如何计算？
- [ ] 加权平均（各维度按权重计算总分）
- [x] 一票否决（功能不正确直接 0 分）
- [ ] 排名制（相对其他 Agent 排名）
- [ ] 其他

**理由**：功能正确性是基础，不正确直接 0 分。正确的前提下，按 token 效率和尝试次数计算分数。具体公式：score = 100 * (1 - token/max_token) * (1 - attempts/max_attempts)。

### 5.4 验收失败后如何处理？
- [x] 返回失败原因，Agent 可重试
- [x] 记录失败案例到错误知识库
- [x] 提供修复建议（基于经验数据）
- [ ] 其他

**理由**：失败是最有价值的学习机会。返回具体失败原因（哪个实体状态不对）、记录到错误知识库、提供修复建议（基于历史相似错误），形成闭环。

## 六、经验提取

### 6.1 竞技场产生的数据如何利用？
- [x] 失败案例 → 错误知识库（自动）
- [x] 成功 flow → 模板库（自动/人工审核）
- [x] DSL bug → 编译器改进
- [x] Agent 行为分析 → 优化 SKILL.md
- [ ] 优质 flow → 经验市场（用户可下载）
- [ ] 其他

**理由**：前四项是竞技场的核心价值，MVP 全部实现。经验市场在 v2.1+。DSL bug 的收集需要人工分析，但数据自动记录。

### 6.2 成功 flow 如何入库？
- [ ] 自动入库（评分超过阈值自动加入模板库）
- [x] 人工审核（dw/用户审核后入库）
- [ ] Agent 自己选择是否贡献
- [ ] 其他

**理由**：自动入库风险高（可能有质量差的 flow）。MVP 阶段人工审核，dw 定期 review 高分 flow，优质的加入模板库。后期可以加自动入库+人工复核。

### 6.3 经验数据是否跨用户共享？
- [x] 是，所有竞技场数据汇总到全局经验库
- [ ] 否，每个用户独立
- [ ] 可选，用户可选择是否贡献
- [ ] 其他

**理由**：竞技场的价值在于数据量。跨用户共享才能积累足够的经验数据。用户开启竞技场时默认同意贡献数据（协议中说明）。敏感信息（设备名、entity_id）可以脱敏。

## 八、安全与风险

### 8.1 竞技场最大的安全风险是什么？
- [x] Agent 编写危险 flow（删除设备、无限循环）
- [x] 竞技场被滥用（刷分、DDoS 设备）
- [ ] 数据泄露（用户设备信息被 Agent 获取）
- [x] 影响生产环境（隔离不彻底）
- [ ] 其他

**理由**：前两项是最大风险。危险 flow 靠安全闸门+静态分析+沙盒执行三重防护。滥用靠 API Key 频率限制+异常检测。数据泄露在 L1 沙盒层不存在（都是虚拟设备）。

### 8.2 如何检测和阻止危险 flow？
- [x] 静态分析（检测危险节点类型）
- [x] 安全闸门（现有 gate 机制）
- [x] 沙盒执行（先在虚拟环境验证）
- [ ] 人工审核（高风险操作需要确认）
- [ ] 其他

**理由**：三层防护。静态分析在编译前检测危险节点（如 exec、debug 到文件）。安全闸门在部署前检查实体授权。沙盒执行是 L1 层本身的特性（虚拟设备随便折腾）。

### 8.3 竞技场是否需要用户明确同意？
- [ ] 是，首次使用需要用户签署协议
- [x] 是，但只需在 WebUI 勾选确认
- [ ] 否，默认安全隔离
- [ ] 其他

**理由**：需要用户确认，但不必太繁琐。WebUI 开启竞技场时弹出说明（风险、数据贡献、隔离机制），用户勾选"我已了解并同意"即可。

## 十一、其他

### 11.1 你认为竞技场模式最大的价值是什么？

**主动获取高质量经验数据。** 现有经验收集是被动的，依赖用户实际使用。竞技场可以标准化任务、批量测试、主动制造成功和失败案例。这些数据可以直接用于：改进 DSL 编译器、优化 SKILL.md、丰富模板库、发现 Agent 的共性错误。长期来看，竞技场积累的数据是 AutoFlow 最大的护城河。

### 11.2 你最担心的问题是什么？

**安全隔离的彻底性。** 虽然设计了独立 NR + vhass，但如果 Agent 编写的 flow 能逃逸出沙盒（比如通过 NR 的 exec 节点执行命令），就可能影响宿主系统。需要：1) 禁用危险节点类型（exec、file out 等）；2) NR 容器以非 root 运行；3) 容器资源限制（CPU/内存）；4) 定期审计竞技场容器的进程和网络。

### 11.3 有什么被遗漏的重要考虑？

1. **任务的可重复性**：同一个任务多次运行，结果应该一致。vhass 的状态需要在每次验收前重置。
2. **并发控制**：多个 Agent 同时验收时，不能互相干扰（各自独立 inject，独立观测）。
3. **数据脱敏**：经验数据跨用户共享时，需要脱敏设备名和 entity_id。
4. **NR 版本兼容性**：竞技场的 NR 版本应该与用户生产环境一致，否则经验数据可能不适用。
5. **任务难度校准**：预定义任务的难度需要实际测试后校准，不能凭感觉分级。

### 11.4 其他想法或建议

1. **竞技场可以作为 CI/CD 的一部分**：AutoFlow 自身的每次更新，可以在竞技场跑一遍标准任务集，验证没有回归。
2. **任务即测试用例**：挑战任务本质上是集成测试用例，可以复用 AutoFlow 的 e2e 验证框架。
3. **先内部使用再开放**：MVP 阶段先由 dw 和 wb2 内部使用，积累数据和经验，稳定后再开放给用户。
4. **竞技场 token 不计费**：竞技场使用的是虚拟设备，token 消耗应该免费或单独统计，不占用用户的生产 token 配额。
