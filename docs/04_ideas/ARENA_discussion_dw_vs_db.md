## 一、答卷关键差异对比

| 维度 | dw | db | 差异分析 | 建议 |
|------|-----|-----|---------|------|
| **NR 部署** | 独立 Docker 容器 | 独立 Docker 容器 | 一致 | 独立容器，但 MVP 可先用 vhass + 独立 tab |
| **设备层级** | L1+L2+L3 | L1+L2（不做L3） | db 更保守 | 同意 db，MVP 只做 L1 |
| **Agent 隔离** | 每个 Agent 独立 tab | 每个 Agent 独立 NR 实例 | **重大差异** | 折中：MVP 独立 tab，v2.1 可选独立实例 |
| **任务定义** | 预定义+用户自定义 | 仅预定义 | db 更保守 | 同意 db，MVP 仅预定义 |
| **时间限制** | 不限时 | 限时（5/10/20/30分钟） | **重大差异** | 同意 db，限时防止 token 失控 |
| **Agent 接入** | Pro API Key | 独立竞技场 Key + MCP | **重大差异** | 同意 db，独立 Key 更安全 |
| **评分维度** | 正确性+token+尝试 | +速度 | db 多了速度 | 同意 db，速度可量化 |
| **激励机制** | 纯技术向 | 徽章/成就 | db 更游戏化 | 折中：徽章成本低可加 |
| **结果存储** | JSON | SQLite | **重大差异** | 同意 db，且 task_store.py 已用 SQLite |
| **MVP 功能** | 5个（含经验提取） | 4个（不含排行榜/经验提取） | db 更精简 | 同意 db，MVP 聚焦核心闭环 |
| **版本数** | 4-5个 | 2-3个 | db 更乐观 | 折中：3-4个，因为已有可复用模块 |

## 二、重大发现：可复用的现有模块

在开始开发前，发现三个核心模块已经存在，可以大幅减少开发量：

### 1. `task_store.py`（849行）— DSL 验证任务池
- **已实现**：SQLite 存储、tasks 表、task_claims 表（认领/状态）、issues 表（缺陷闭环）
- **功能**：任务灌入（publish）、随机认领（claim）、指定认领、entity_hint 富化、重试管理
- **复用方式**：直接作为竞技场的任务系统，增加难度分级和验收标准字段

### 2. `vhass.py`（579行）— 虚拟 HA
- **已实现**：纯标准库的虚拟 Home Assistant，数字孪生 / staging 数据源
- **复用方式**：直接作为竞技场 L1 沙盒层的设备模拟，不需要额外 Docker 容器

### 3. `proposals.py`（671行）— 提案/经验沉淀
- **已实现**：raw→candidate→public 升格流程，经验落盘公用 skill
- **复用方式**：作为竞技场的经验提取管道，成功 flow → candidate → 人工审核 → public 模板

**结论**：竞技场 MVP 的开发量比预期小很多，因为任务池、虚拟设备、经验沉淀三个核心模块都已存在。

## 三、5 个关键问题讨论

### 问题 1：独立容器会是过度设计吗？

**我的观点：不是过度设计，但可以分阶段实现。**

**理由**：
- 竞技场的核心理念是"安全地失败"，隔离是生命线
- 但 MVP 阶段不需要上来就独立 NR 容器，因为：
  1. `vhass.py` 已经存在，可以提供虚拟设备，Agent 操作的是虚拟设备，不会影响真实设备
  2. 可以复用生产 NR，但使用**独立 tab + 独立 flow 命名空间**，flow 之间互不干扰
  3. 竞技场的 flow 只连接 vhass 虚拟设备，不连接真实设备

**分阶段方案**：
- **v2.0 MVP**：复用生产 NR + 独立 tab + vhass 虚拟设备（轻量，快速验证）
- **v2.1**：可选独立 NR 容器（用户可选择隔离级别）
- **v2.2**：多 Agent 并发时自动创建临时 NR 实例

**风险控制**：即使复用生产 NR，也必须：
1. 竞技场 flow 的节点 ID 加 `arena_` 前缀
2. 安全闸门禁止竞技场 flow 操作非 vhass 设备
3. 竞技场 tab 与生产 tab 物理隔离（不同 tab）

### 问题 2：命题作文 vs 自由作文？

**我的观点：两者结合，但 MVP 先做命题作文，自由作文作为 v2.1 的高价值功能。**

**命题作文（挑战任务）的价值**：
- 标准化评估，可对比不同 Agent
- 明确验收标准，可自动评分
- 可复用 `task_store.py`，开发量小
- 适合收集 DSL bug 和失败模式

**自由作文（沙盒创造）的价值**：
- 激发 Agent 创造力，可能发现人类没想到的 flow 用法
- 收集优质 flow（命题作文的答案是已知的，自由作文可能产出新奇方案）
- 更接近真实使用场景（用户不会给 Agent 出命题作文）

**自由作文的难点**：
- 没有明确验收标准，无法自动评分
- 需要"创意评分"机制（LLM 评估 + 人工审核）
- 资源消耗不可控（Agent 可能写非常复杂的 flow）

**建议方案**：
- **v2.0 MVP**：命题作文（10-20个预定义任务，4级难度）
- **v2.1**：增加自由作文模式
  - 提供一组 vhass 虚拟设备 + 设备历史数据
  - Agent 自由编写 flow，系统记录 flow 结构
  - 评分用"创意分"（LLM 评估：新颖性、实用性、复杂度）
  - 优质 flow 自动进入"待审核模板库"
- **两者共享**：经验数据、错误知识库、排行榜

### 问题 3：之前的 DSL 任务池可以复用吗？

**答案：完全可以，而且是竞技场的核心基础设施。**

`task_store.py` 已经实现了：
- SQLite 数据库（与 db 的选择一致）
- tasks 表：任务定义（id、tier、scene_name、task_text、entity_hint）
- task_claims 表：任务认领（task_id、agent_id、status、retries）
- issues 表：缺陷闭环
- 任务灌入、随机认领、指定认领、entity_hint 富化

**需要扩展的字段**：
- `difficulty`：难度分级（easy/medium/hard/hell）
- `acceptance_criteria`：验收标准（JSON，定义触发后期望的实体状态）
- `timeout_seconds`：超时时间
- `max_attempts`：最大尝试次数
- `devices_required`：需要的虚拟设备列表

**复用方式**：
- 竞技场的任务系统直接基于 `task_store.py` 扩展
- 现有的任务数据（如果有的话）可以直接导入竞技场
- MCP 的 `mcp-admin` 已经有任务池相关工具，可以复用

**结论**：任务池不是"可以复用"，而是"应该直接用"。这节省了至少 2-3 周的开发量。

### 问题 4：memory-agent 创造力对照实验？

**我的观点：这是竞技场的杀手级应用，必须做。**

**为什么价值巨大**：
1. **量化 memory-agent 的价值**：目前 memory-agent 的价值是主观的，竞技场可以用数据证明"用了 memory-agent 的 Agent 成功率高 X%，token 省 Y%"
2. **迭代 memory-agent**：通过对照实验发现 memory-agent 的不足（比如记忆检索不准、上下文太长等）
3. **天然的 A/B 测试环境**：竞技场支持多 Agent，可以随机分组

**实验设计**：
- **A 组（对照组）**：Agent 只用 AutoFlow Pro
- **B 组（实验组）**：Agent 用 AutoFlow Pro + memory-agent
- **相同任务集**：两组执行相同的挑战任务
- **对比指标**：成功率、平均 token、平均完成时间、尝试次数、flow 质量

**需要注意的问题**：
1. **token 统计要分开**：memory-agent 的 token 消耗单独统计，否则对比不公平
2. **记忆隔离**：不同 Agent 的记忆不能互相污染
3. **记忆预热**：实验开始前 memory-agent 的记忆状态要一致（都为空或都加载相同的基础记忆）
4. **样本量**：需要足够多的任务和重复次数才能得出统计显著的结论

**实现方式**：
- 竞技场增加"实验模式"：用户可以创建对照实验，指定 A/B 组配置
- memory-agent 增加"竞技场模式"：精简记忆接口，只返回与当前任务相关的记忆
- 实验结果自动生成对比报告

### 问题 5：Pro + memory-agent token 会非常庞大吗？需要更强联系吗？

**答案：是的，token 会显著增加。需要设计专门的竞技场接口。**

**token 膨胀的原因**：
1. memory-agent 需要读取历史记忆（可能很长）
2. 每次操作后需要写入新记忆
3. memory-agent 本身可能需要多次 LLM 调用（检索、总结、生成建议）
4. Agent 需要把 memory-agent 的回复纳入上下文

**估算**：
- 纯 Pro：每次 propose-dsl 约 500-2000 token（DSL + 响应）
- Pro + memory-agent：每次操作可能增加 1000-5000 token（记忆检索 + 建议）
- 总 token 可能增加 2-5 倍

**解决方案：memory-agent 竞技场专用接口**

设计一个轻量级接口，而不是让 Agent 直接使用完整的 memory-agent：

```
Agent → 竞技场网关 → memory-agent（精简模式）
```

**精简模式的特点**：
1. **任务上下文感知**：只返回与当前挑战任务相关的记忆
2. **记忆预加载**：Agent 认领任务时，一次性加载相关记忆，后续只写不读
3. **失败触发建议**：只有在 Agent 失败时，memory-agent 才提供针对性建议（不是全程陪伴）
4. **记忆缓存**：相同任务的记忆可以缓存，避免重复检索
5. **token 预算**：memory-agent 有独立的 token 预算，超出后自动降级为"仅记录不建议"

**更强的联系：事件驱动架构**

不是 Agent 主动查询 memory-agent，而是 memory-agent 订阅竞技场事件：
- Agent 认领任务 → memory-agent 预加载相关记忆
- Agent 提交失败 → memory-agent 自动生成修复建议
- Agent 提交成功 → memory-agent 记录成功经验
- 任务完成 → memory-agent 总结本次经验

这样 Agent 不需要额外调用 memory-agent，token 增加最小化。

**实现优先级**：
1. v2.0：memory-agent 独立运行，Agent 可选使用（token 自担）
2. v2.1：竞技场专用记忆接口（精简模式）
3. v2.2：事件驱动架构（memory-agent 订阅竞技场事件）

## 四、综合建议：竞技场 v2.0 修订方案

基于以上讨论，修订竞技场 MVP 方案：

### 核心原则
1. **复用优先**：task_store.py + vhass.py + proposals.py 直接用
2. **安全第一**：vhass 虚拟设备 + 独立 tab + 节点前缀
3. **命题先行**：MVP 只做命题作文，自由作文 v2.1
4. **数据闭环**：失败→错误库，成功→待审核模板
5. **memory-agent 友好**：预留对照实验接口

### v2.0 MVP 功能（3个版本）
- **v2.0.0-alpha**：vhass 集成 + task_store 扩展（任务难度/验收标准）+ 竞技场 API Key
- **v2.0.0-beta**：Agent 接入（propose-dsl 关联任务）+ 自动验收引擎（inject 触发 + 状态对比）
- **v2.0.0**：基础 WebUI + 排行榜 + 经验提取（失败→错误库，成功→待审核）

### v2.1 规划
- 自由作文模式
- memory-agent 竞技场专用接口
- 对照实验模式
- 独立 NR 容器选项

### 关键决策（需要 db 确认）
1. MVP 复用生产 NR + 独立 tab，还是直接独立 NR 容器？
2. 自由作文放在 v2.1 是否合适？
3. memory-agent 对照实验是否纳入 v2.1？
4. task_store.py 的现有任务数据是否需要迁移？
