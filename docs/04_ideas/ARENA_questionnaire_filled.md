## 一、目标与定位

### 1.1 竞技场的核心目标是什么？（可多选）
- [x] 收集经验数据（失败案例、DSL bug、优质 flow）
- [x] 评估不同 Agent 的能力（排行榜、对比）
- [ ] 让用户娱乐化地使用 AutoFlow（游戏化）
- [x] 验证 AutoFlow Pro 的稳定性和安全性
- [ ] 其他：__________

**理由**：竞技场的核心价值是"压力测试 + 经验提取"。通过多 Agent 竞争，快速暴露 DSL 编译器 bug、安全闸门漏洞，并积累优质 flow 模板。排行榜是副产品，用于激励 Agent 开发者参与。娱乐化不是主要目标，但可以作为锦上添花。

### 1.2 竞技场的主要用户是谁？
- [x] Agent 开发者（测试自己的 Agent）
- [ ] 普通用户（看排行榜、用优质 flow）
- [x] AutoFlow 开发者（收集 bug 和经验）
- [ ] 其他：__________

**理由**：初期主要用户是 Agent 开发者和 AutoFlow 开发者自己。Agent 开发者用竞技场测试和优化自己的 Agent，AutoFlow 开发者通过竞技场收集 bug 和经验数据。普通用户后期可以通过排行榜发现优质 flow，但不是初期重点。

### 1.3 竞技场与现有 Pro 版的关系？
- [x] 独立模块，Pro 用户可选开启
- [ ] Pro 版的内置功能，默认开启
- [ ] 独立部署，与生产环境完全隔离
- [ ] 其他：__________

**理由**：竞技场是 Pro 版的高级功能，用户可以选择开启或关闭。默认关闭，避免影响生产环境。开启后使用独立的 NR 实例和虚拟设备，与生产环境逻辑隔离但物理上可以同机部署。独立部署太重，初期不考虑。

## 二、架构与隔离

### 2.1 竞技场的 NR 实例如何部署？
- [x] 独立 Docker 容器，与生产 NR 完全隔离
- [ ] 复用生产 NR，但使用独立 tab（命名空间隔离）
- [ ] 云端共享 NR 实例，多用户共用
- [ ] 其他：__________

**理由**：必须完全隔离。竞技场会频繁部署/删除 flow，可能触发无限循环或错误操作，复用生产 NR 风险太大。独立 Docker 容器可以随时重置，不影响生产。云端共享初期不考虑（自部署为主）。

### 2.2 设备来源有哪些层级？（可多选）
- [x] L1：vhass 虚拟设备（完全模拟，无真实影响）
- [x] L2：真实设备只读/限频（不影响生产，但能读真实状态）
- [ ] L3：用户授权的真实设备（可写，但严格配额）
- [ ] 其他：__________

**理由**：MVP 只做 L1（vhass 虚拟设备），完全安全。L2（真实设备只读）作为第二阶段，可以让 Agent 看到真实设备状态但不能操作，增加真实感。L3（可写真实设备）风险太高，初期不做，后期可以考虑但需要严格的安全闸门和用户明确授权。

### 2.3 如何防止竞技场影响生产环境？
- [x] 完全独立的 NR + HA 实例
- [x] 网络隔离（不同 VLAN / Docker 网络）
- [x] 设备白名单（只有授权设备可被操作）
- [x] 频率限制（单位时间内最多操作 N 次）
- [x] 操作审计（所有操作可追溯）
- [ ] 其他：__________

**理由**：多层防护，缺一不可。独立实例是基础，网络隔离防止误连生产，设备白名单防止操作未授权设备，频率限制防止 DDoS，操作审计用于事后追溯。安全是竞技场的生命线。

### 2.4 多个 Agent 同时编写 flow 时如何隔离？
- [ ] 每个 Agent 独立 tab（当前模式）
- [x] 每个 Agent 独立 NR 实例
- [ ] 共享 tab，但节点 ID 加 Agent 前缀
- [ ] 其他：__________

**理由**：独立 NR 实例最彻底。多个 Agent 同时写 flow 时，如果共享 NR，一个 Agent 的错误 flow 可能影响其他 Agent（比如触发无限循环占用资源）。每个 Agent 一个独立的 NR 容器，用完即销毁，最安全。成本可以接受（NR 容器很轻量）。

## 三、挑战任务设计

### 3.1 挑战任务如何定义？
- [x] 预定义任务库（官方维护，按难度分级）
- [ ] 用户自定义任务（用户创建挑战）
- [ ] 两者都支持
- [ ] 其他：__________

**理由**：MVP 只做预定义任务库。用户自定义任务需要任务验证机制（确保任务可完成、验收标准明确），复杂度高。后期可以开放用户自定义，但需要审核机制。预定义任务库由官方维护，保证质量和可验收性。

### 3.2 任务难度如何分级？
- [x] 简单（单 trigger 单 action，如"开灯"）
- [x] 中等（多条件、多 action，如"温度高且有人时开空调"）
- [x] 困难（复杂逻辑、错误处理、多设备联动）
- [x] 地狱（边界情况、并发、状态机）
- [ ] 其他：__________

**理由**：四级分级覆盖从入门到极限。简单任务用于验证基础能力，中等任务验证常用场景，困难任务验证复杂逻辑，地狱任务用于压力测试和暴露边界 bug。每级 10-20 个任务，总共 50-80 个任务作为初始库。

### 3.3 任务的验收标准是什么？（可多选）
- [x] 触发 inject 后，HA 实体状态符合预期
- [x] flow 能正确编译并部署
- [x] flow 不包含危险操作（如删除所有设备）
- [x] token 消耗在合理范围内
- [ ] flow 可维护性（节点命名、注释）
- [ ] 其他：__________

**理由**：前三项是硬性验收标准（必须通过），token 消耗是评分维度（不是硬性标准）。可维护性作为加分项，不纳入 MVP 验收（主观判断难自动化）。危险操作检测复用现有安全闸门。

### 3.4 任务是否有时间限制？
- [x] 有，每个任务限时 N 分钟
- [ ] 没有，Agent 可以慢慢写
- [ ] 分阶段，简单任务限时，困难任务不限时
- [ ] 其他：__________

**理由**：必须有时间限制。没有时间限制会导致 token 消耗不可控，而且排行榜的"速度"维度也无法计算。建议：简单 5 分钟，中等 10 分钟，困难 20 分钟，地狱 30 分钟。超时算失败，但可以记录部分成果。

## 四、Agent 接入

### 4.1 Agent 如何接入竞技场？
- [ ] 通过 Pro 版 API Key（与现有 Pro 一致）
- [x] 独立的竞技场 API Key（与生产隔离）
- [x] MCP 接口（Agent 通过 MCP 调用）
- [ ] WebSocket 实时接口（更高效）
- [ ] 其他：__________

**理由**：独立 API Key 是必须的（与生产隔离，防止竞技场 Key 被滥用来操作生产）。MCP 接口作为主要接入方式（与 AutoFlow 现有 MCP 生态一致）。Pro 版 API Key 不应该能直接调用竞技场（需要单独申请竞技场 Key）。

### 4.2 Agent 如何知道当前挑战任务？
- [x] API 查询任务列表和详情
- [x] 任务描述通过 prompt 注入给 Agent
- [ ] WebUI 展示任务，用户复制给 Agent
- [ ] 其他：__________

**理由**：API 查询是基础（Agent 可以拉取任务列表、选择任务、获取任务详情）。任务描述通过 prompt 注入是标准做法（把任务描述、验收标准、设备列表等注入给 Agent）。WebUI 复制是给人类用户用的，不是 Agent 的主要方式。

### 4.3 Agent 提交 flow 的方式？
- [x] propose-dsl（DSL 优先，与现有一致）
- [x] deploy-raw（raw JSON，逃生舱）
- [ ] 两者都支持
- [ ] 其他：__________

**理由**：与现有 Pro 版保持一致。propose-dsl 是主要方式（经过编译器验证），deploy-raw 是逃生舱（编译器搞不定时用）。竞技场应该鼓励 propose-dsl，但不禁止 deploy-raw（可以分别统计两种方式的成功率）。

### 4.4 是否允许 Agent 多次尝试？
- [x] 允许，每个任务最多 N 次尝试
- [ ] 不限次数，但每次尝试消耗 token
- [ ] 只允许一次提交
- [ ] 其他：__________

**理由**：有限次数更合理。建议：简单 3 次，中等 5 次，困难 7 次，地狱 10 次。每次尝试消耗 token（Agent 自己承担成本），最后一次的成绩作为最终成绩。不限次数会导致 token 消耗不可控，一次提交太严格（不符合真实开发流程）。

## 五、验收与评分

### 5.1 验收如何执行？
- [x] 自动触发 inject 节点，观测 HA 状态变化
- [x] 静态分析 flow 结构（节点类型、连接关系）
- [ ] 人工审核（复杂任务需要人判断）
- [ ] 其他：__________

**理由**：MVP 必须全自动验收。自动触发 inject + 状态对比是核心（功能正确性的客观验证）。静态分析用于安全检查和结构评分。人工审核成本太高，初期不做（后期可以对"地狱"级任务引入人工审核作为加分项）。

### 5.2 评分维度有哪些？（可多选）
- [x] 功能正确性（是否完成任务）
- [x] token 效率（消耗越少分越高）
- [x] 尝试次数（越少分越高）
- [ ] flow 质量（可维护性、注释）
- [x] 速度（完成时间越短分越高）
- [ ] 创新性（非显而易见的解法）
- [ ] 其他：__________

**理由**：前四项是可量化的客观维度。功能正确性是基础（占 50% 权重），token 效率、尝试次数、速度是效率维度（各占 15-20%）。flow 质量和创新性主观判断难自动化，初期不纳入评分（可以作为"编辑推荐"标签，人工评选）。

### 5.3 评分如何计算？
- [x] 加权平均（各维度按权重计算总分）
- [x] 一票否决（功能不正确直接 0 分）
- [ ] 排名制（相对其他 Agent 排名）
- [ ] 其他：__________

**理由**：一票否决 + 加权平均结合。功能不正确直接 0 分（一票否决），功能正确的情况下按加权平均计算总分（功能正确性 50% + token 效率 20% + 尝试次数 15% + 速度 15%）。排名制作为排行榜的展示方式，但基础分是绝对分（不是相对分）。

### 5.4 验收失败后如何处理？
- [x] 返回失败原因，Agent 可重试
- [x] 记录失败案例到错误知识库
- [x] 提供修复建议（基于经验数据）
- [ ] 其他：__________

**理由**：三项都做。返回失败原因是基础（告诉 Agent 哪里错了），记录失败案例是竞技场的核心价值之一（自动积累错误知识库），提供修复建议是增值服务（基于历史失败案例和修复方案，帮助 Agent 快速改进）。

## 六、经验提取

### 6.1 竞技场产生的数据如何利用？（可多选）
- [x] 失败案例 → 错误知识库（自动）
- [x] 成功 flow → 模板库（自动/人工审核）
- [x] DSL bug → 编译器改进
- [x] Agent 行为分析 → 优化 SKILL.md
- [ ] 优质 flow → 经验市场（用户可下载）
- [ ] 其他：__________

**理由**：前四项是核心价值。失败案例自动入库（竞技场的主要目的），成功 flow 评分超过阈值后自动进入"待审核"队列，人工审核后入库。DSL bug 通过失败案例分析发现，反馈给编译器开发。Agent 行为分析用于优化 SKILL.md（发现 Agent 常犯的错误，在 SKILL.md 中增加提醒）。经验市场后期再做。

### 6.2 成功 flow 如何入库？
- [ ] 自动入库（评分超过阈值自动加入模板库）
- [x] 人工审核（dw/用户审核后入库）
- [ ] Agent 自己选择是否贡献
- [ ] 其他：__________

**理由**：必须人工审核。自动入库风险太高（可能有隐藏的安全问题、可维护性差、或者只是碰巧通过验收）。流程：评分超过阈值 → 自动进入"待审核"队列 → dw 或社区审核者审核 → 通过后入库，不通过的标注原因。审核标准：安全性、可维护性、通用性、注释完整性。

### 6.3 经验数据是否跨用户共享？
- [x] 是，所有竞技场数据汇总到全局经验库
- [ ] 否，每个用户独立
- [ ] 可选，用户可选择是否贡献
- [ ] 其他：__________

**理由**：竞技场的价值在于数据量，跨用户共享才能快速积累足够的失败案例和成功模板。自部署场景下，每个用户的竞技场数据可以选择是否上报到全局经验库（默认上报，可关闭）。上报的数据匿名化（不包含用户设备信息、API Key 等敏感数据）。

## 七、排行榜与激励

### 7.1 是否需要排行榜？
- [ ] 需要，按总分排名
- [x] 需要，分维度排名（成功率、token 效率等）
- [ ] 不需要，竞技场只是工具不是游戏
- [ ] 其他：__________

**理由**：分维度排名更有价值。单一总分排名容易被"刷分"（比如只做简单任务）。分维度排名包括：总成功率、平均 token 效率、平均完成速度、困难任务完成数、地狱任务完成数等。这样不同特点的 Agent 都有机会上榜（有的 Agent 快但费 token，有的 Agent 慢但省 token）。

### 7.2 排行榜展示哪些信息？（可多选）
- [x] Agent 名称/ID
- [x] 完成任务数
- [x] 成功率
- [x] 平均 token 消耗
- [x] 平均完成时间
- [x] 优质 flow 数
- [ ] 其他：__________

**理由**：这些都是可量化的客观指标。Agent 名称/ID 是基础，完成任务数和成功率反映能力，平均 token 消耗和完成时间反映效率，优质 flow 数反映贡献。还应该展示每个 Agent 的"擅长领域"（比如简单任务成功率高、困难任务完成数多）。

### 7.3 是否有激励机制？
- [x] 徽章/成就（完成特定任务获得）
- [ ] 经验值/等级
- [ ] 实物/虚拟奖励
- [ ] 没有，纯技术向
- [ ] 其他：__________

**理由**：徽章/成就成本低、趣味性强。比如："首次完成地狱任务"、"100 任务无失败"、"token 效率大师"、"速度之王"等。经验值/等级可以做但不是重点，实物/虚拟奖励初期不考虑（自部署场景没有商业化）。纯技术向太枯燥，适当的游戏化可以增加参与度。

## 八、安全与风险

### 8.1 竞技场最大的安全风险是什么？（可多选）
- [x] Agent 编写危险 flow（删除设备、无限循环）
- [x] 竞技场被滥用（刷分、DDoS 设备）
- [x] 数据泄露（用户设备信息被 Agent 获取）
- [x] 影响生产环境（隔离不彻底）
- [ ] 其他：__________

**理由**：四项都是重大风险。危险 flow 是最直接的风险（安全闸门必须拦住），被滥用是运营风险（API Key 配额 + 频率限制），数据泄露是隐私风险（虚拟设备不包含真实设备信息），影响生产是架构风险（完全隔离）。安全设计必须覆盖所有四个维度。

### 8.2 如何检测和阻止危险 flow？
- [x] 静态分析（检测危险节点类型）
- [x] 安全闸门（现有 gate 机制）
- [x] 沙盒执行（先在虚拟环境验证）
- [ ] 人工审核（高风险操作需要确认）
- [ ] 其他：__________

**理由**：三层防护。静态分析是第一道（检测危险节点类型、可疑连接），安全闸门是第二道（现有 gate 机制，包括密钥门禁、危险操作拦截），沙盒执行是第三道（先在 vhass 虚拟环境跑一遍，确认没有无限循环、没有异常操作后才算通过）。人工审核成本太高，初期不做（后期可以对高风险任务引入）。

### 8.3 竞技场是否需要用户明确同意？
- [ ] 是，首次使用需要用户签署协议
- [x] 是，但只需在 WebUI 勾选确认
- [ ] 否，默认安全隔离
- [ ] 其他：__________

**理由**：需要用户明确同意，但不需要签署协议（太重）。首次开启竞技场时，WebUI 弹出确认框，说明：①竞技场使用独立 NR 实例和虚拟设备，②不会影响生产环境，③竞技场数据会匿名上报到全局经验库（可关闭），④用户承担 Agent token 消耗成本。用户勾选"我已阅读并同意"后才能开启。

## 九、技术实现

### 9.1 竞技场的代码放在哪里？
- [x] 现有网关内增加 /api/arena/* 接口
- [ ] 独立服务（arena_server），与网关通信
- [ ] 独立项目（AutoFlow Arena）
- [ ] 其他：__________

**理由**：MVP 放在现有网关内，减少部署复杂度。竞技场需要复用网关的很多能力（propose-dsl、安全闸门、错误知识库、模板库），独立服务会增加通信成本。后期如果竞技场逻辑太复杂，可以拆分成独立服务，但初期不拆。接口前缀 /api/arena/*，与现有接口隔离。

### 9.2 挑战任务如何存储？
- [x] JSON 文件（与现有数据存储一致）
- [ ] 数据库（SQLite/PostgreSQL）
- [ ] Git 仓库（任务即代码，可 PR）
- [ ] 其他：__________

## 十、开发优先级

### 10.1 竞技场 v2.0 MVP 应该包含哪些功能？（选最重要的 3-5 个）
- [x] L1 沙盒层（独立 NR + vhass）

- [x] 自动验收（触发 + 状态对比）
- [ ] 排行榜
- [ ] 经验自动提取
- [ ] WebUI 竞技场页面
- [ ] 其他：__________

**理由**：MVP 只做最核心的 4 项。L1 沙盒层是基础（没有安全隔离就没有竞技场），挑战任务系统是内容（没有任务就没有挑战），Agent 接入是入口（没有 Agent 就没有参与者），自动验收是裁判（没有验收就没有评分）。排行榜、经验提取、WebUI 都可以在 v2.1 做（MVP 可以用命令行查看结果）。

### 10.2 开发顺序应该是？
1. **L1 沙盒层**（独立 NR 容器管理 + vhass 集成）
2. **挑战任务系统**（任务定义、任务库、任务选择）
3. **Agent 接入**（竞技场 API Key、MCP 接口、propose-dsl 提交）
4. **自动验收引擎**（inject 触发、状态对比、超时控制、多次尝试管理）
5. **基础 WebUI + 排行榜**（任务列表、成绩查看、简单排行榜）

**理由**：按依赖关系排序。沙盒层是基础（其他都依赖它），任务系统是内容（Agent 需要知道做什么），Agent 接入是入口（Agent 需要能提交 flow），自动验收是核心（判断 Agent 做得好不好），WebUI 和排行榜是展示（最后做）。

### 10.3 预计 v2.0 MVP 需要多少个版本？
- [x] 2-3 个小版本
- [ ] 4-5 个小版本
- [ ] 6+ 个小版本
- [ ] 不确定

## 十一、其他

### 11.1 你认为竞技场模式最大的价值是什么？

**自动化压力测试 + 经验数据飞轮。**

传统的 AutoFlow 开发依赖人工测试和用户反馈，速度慢、覆盖窄。竞技场通过多 Agent 自动竞争，可以在短时间内运行成千上万次 flow 编写尝试，快速暴露 DSL 编译器的边界 bug、安全闸门的漏洞、SKILL.md 的不足。

更重要的是形成**数据飞轮**：失败案例 → 错误知识库 → Agent 学习避免 → 更少失败 → 更难的任务 → 暴露更深层的问题。成功 flow → 模板库 → 用户直接使用 → 收集真实反馈 → 优化模板。这个飞轮转起来后，AutoFlow 的质量会加速提升。

### 11.2 你最担心的问题是什么？

**安全隔离的彻底性。**

竞技场的核心理念是"安全地失败"，但如果隔离不彻底，一次失败就可能影响生产环境，造成不可挽回的损失（比如误删设备、触发危险操作）。

具体担心：
1. **NR 隔离不彻底**：独立容器但共享 Docker 网络，可能被 Agent 探测到生产 NR 的地址
2. **设备隔离不彻底**：vhass 虚拟设备可能意外连接到真实 HA 实例
3. **资源隔离不彻底**：一个 Agent 的无限循环 flow 可能耗尽宿主机资源，影响其他容器
4. **数据隔离不彻底**：竞技场的错误日志可能包含生产环境的敏感信息（设备名、API Key 等）

应对方案：多层隔离 + 定期渗透测试 + 默认关闭（用户明确同意后才开启）。

### 11.3 有什么被遗漏的重要考虑？

**1. Agent 身份管理和防作弊**
- 如何防止同一个 Agent 用多个 API Key 刷分？
- 如何检测 Agent 之间的"串通"（互相抄答案）？
- 排行榜的可信度如何保证？

**2. 任务库的版本管理**
- 任务修改后，历史成绩如何处理？（任务变了，旧成绩可能不再有效）
- 任务库如何升级？（新增任务、修改验收标准、废弃过时任务）

**3. 竞技场的运营成本**
- 多 Agent 同时运行时，NR 容器和 vhass 的资源消耗如何控制？
- 数据库（验收结果）的增长速度如何？需要定期清理吗？
- 全局经验库的上报和同步机制如何设计？

**4. 与现有 Pro 版的协同**
- 竞技场发现的 DSL bug 如何快速反馈到 Pro 版编译器？
- 竞技场积累的优质模板如何同步到 Pro 版模板库？
- Pro 版用户的失败案例能否"回流"到竞技场作为挑战任务？

### 11.4 其他想法或建议

**1. 先做"单人模式"再做"多人竞技"**
MVP 可以先支持单个 Agent 挑战任务（类似刷题），验证沙盒层、任务系统、自动验收的可行性。多人同时竞技、排行榜、对比等功能可以在 v2.1 做。这样降低 MVP 复杂度，快速验证核心价值。

**2. 竞技场作为"Pro 版测试环境"**
竞技场的独立 NR + vhass 不仅可以用于 Agent 竞争，也可以作为 Pro 版用户的"安全测试环境"——用户可以先在竞技场里测试 flow，确认没问题后再部署到生产。这样竞技场的价值不局限于 Agent 竞争，也面向人类用户。

**3. 经验数据的"双向流动"**
不仅竞技场 → 经验库，也要经验库 → 竞技场。Agent 进入竞技场时，可以选择是否加载全局经验库（加载后 Agent 可以看到历史失败案例和修复建议，减少重复犯错）。这样新 Agent 不需要从零开始，可以站在"前人的肩膀"上。

**4. 定期"赛季"机制**
排行榜可以按"赛季"重置（比如每月一个赛季），每个赛季有不同的主题（比如"本月主打多设备联动"、"本月主打错误处理"）。赛季结束后评选"赛季最佳 Agent"，颁发徽章。这样保持长期新鲜感，避免排行榜固化。
