## 三、发现的收敛点（需评审定性）

以下为清点中发现的**不对称 / 疑似越界**，全部属「是否改、改成什么」的判断题，**待评审**：

| 编号 | 现象 | 风险/影响 | 建议（待评审） |
|------|------|----------|---------------|
| **F1** | `autoflow_ask_llm` 只在**用户服务器**、**不在管理服务器** | admin 反而缺 LLM 助手；三面板不对称 | 补 `@mcp_admin.tool()` 双挂（低风险，建议直接修） |
| **F2** | `autoflow_trigger_inject` **普通可见** | 触发 NR inject 节点**有副作用**（开灯/TTS/微信等），疑似越过「agent 不自批准写操作」边界 | **重点评审**：① 下沉 `_DEPLOY_KNIVES`（专家可见）？ ② 归 admin-only？ ③ 或加确认闸？——取决于它是否被 Pro 引导流程依赖 |
| **F3** | `autoflow_get_nr_flow` **普通可见** | 暴露原始 NR flow JSON，对小白无意义、对普通 agent 是技术噪音 | 下沉 `_DEPLOY_KNIVES`（专家可见） |
| **F4** | `autoflow_debug_read` **普通可见** | 调试读，偏专家；但只读、无副作用 | 可保留（低危）或下沉 experts；待定 |
| **F5** | 普通面 28 把含多把发现类：`list_entities`/`list_automations`/`list_templates`/`list_tabs`/`list_tasks`/`list_decisions`/`list_pending` + `get_*` ×N | 与用户既有诉求一致：「发现类工具过多、重叠、使使用者无所适从」 | 评估合并/收敛（如「列实体/列自动化」是否可统一入口 + 参数），**但**须守住「不引导猜域、最小可用集」两条 |
| **F6** | 用户服务器有 6 把不在管理服务器：`ask_llm`/`debug_read`/`delegate_to_memory_worker`/`get_inventory`/`get_nr_flow`/`trigger_inject` | 面板不对称（admin 看不到这些） | 逐项评审是否补挂 admin |
| **F7** | 普通面存在 `delegate_to_memory_worker`（跨仓反向委托） | 与 ACP 委托链相关 | 确认是否应限专家（与 C-A3 令牌轮换一并看） |

## 四、建议的三档最小集（待评审后实施）

> 原则（沿用用户既定偏好）：**使用者视角、最小可用集、运维刀隔离、不引导猜域、发现类不堆叠**。

**Pro 用户面（normal，建议目标 ≤ 20 把）**
- 身份/求助：`whoami`、`dsl_help`、`get_skill`
- 实体解析：`resolve_entity`、`list_entities`、`get_entity_state`
- 意图→提案：`propose_dsl`
- 任务池（Pro 引导用）：`list_tasks`、`claim_task`、`submit_result`
- 协作/进度：`set_plan`、`request_decision`、`get_decision`、`report_issue`
- 模板：`list_templates`、`render_template`
- **移出普通面**（下沉专家/管理）：`trigger_inject`(F2)、`get_nr_flow`(F3)、`debug_read`(F4)、`ask_llm`(F1→可留但需明确定位)、`delegate_to_memory_worker`(F7 待定)

**Core 专家面（expert = 普通面 + 部署刀）**
- 上述 Pro 面 **+** `_DEPLOY_KNIVES` 16 把（`get_flow`、`list_tabs`、`refresh_catalog`、`list_automations`、`get_inventory` 等 Core 手术刀/盘点也在专家可见）

**Admin 运维面（developer）**
- 全量 **+** 7 把运维刀；**新增**：把 F1/F6 的用户工具补齐到 admin 以对齐面板。
