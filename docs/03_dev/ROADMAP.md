> **创建时间**：2026-09-05
> **负责人**：dw
> **当前版本**：v1.5.6
> **原则**：开发迭代 → 集中测试 → 修复发布，按阶段推进，不频繁打断

---

## 一、总体节奏

```
开发迭代（2-3个小版本）→ 集中测试（wb2）→ 修复发布（稳定版）→ 下一阶段
```

**规则**：
1. **dw 自行验证**：每个版本提交前做语法检查 + 冒烟测试（curl 验证核心接口）
2. **不频繁测试**：每 2-3 个开发版本后集中开工单给 wb2
3. **P0/P1 立即修**：测试发现的阻断/安全 bug 立即修复，不等下一轮
4. **阶段结束回归**：每个 Phase 结束时做一次全面回归测试，发布稳定版

## 六、测试策略详解

### 6.1 dw 自验（每个版本必做）

```
1. python -m py_compile 所有修改的 .py 文件
2. node -e new Function(app.js) 验证前端语法
3. 提交后部署到 NAS
4. curl 验证核心接口（version、propose-dsl、entities）
5. 检查容器日志无报错
```

### 6.2 wb2 集中测试（每 2-3 个版本一次）

```
1. dw 开工单到 share/AutoFlowTestv2/tests/
2. 工单包含：测试版本、环境、用例、预期结果、注意事项
3. wb2 执行测试，返回结果 + 证据
4. dw 分析结果，修复 P0/P1 bug
5. 修复后 dw 自验，必要时再开一轮回归
```

### 6.3 阶段结束回归（每个 Phase 结束）

```
1. 全功能回归测试（覆盖该 Phase 所有功能）
2. 性能测试（响应时间、token 消耗）
3. 安全测试（授权越界、吊销、频率限制）
4. 兼容性测试（不同 Agent、不同 NR 版本）
5. 发布稳定版
```

## 七、版本号规则

| 版本号 | 含义 | 发布频率 |
|--------|------|---------|
| v1.5.x | Pro 版开发迭代 | 频繁（功能完成即发布） |
| v1.6.0 | Pro 版稳定版 | Phase 2 结束 |
| v1.6.x | 经验复用开发迭代 | 频繁 |
| v1.7.0 | 经验复用稳定版 | Phase 3 结束 |
| v2.x.x | 竞技场模式 | Phase 4 |

**规则**：
- 开发迭代版本（x.y.z 中 z 变化）：功能完成即发布，不等待测试
- 稳定版本（x.y.0 中 y 变化）：集中测试 + 全量修复后发布
- Bug 修复：递增 z，立即发布
