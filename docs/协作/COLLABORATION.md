## 一、团队分工

### 角色定义

| 角色 | 负责人 | 职责 | 不负责 |
|------|--------|------|--------|
| **项目负责人** | dw | 架构设计、新功能开发、版本发布、最终代码审查、竞技场 v2.0 | 日常 bug 修复、测试编写、前端微调 |
| **FlowForge Labs (FFL)** | Hermes 团队 (PM + 前端 + 后端 + 测试) | bug 修复、自动化测试、性能优化、安全加固、前端改进 | 架构决策、新功能设计、版本发布 |
| **测试验证** | wb2 | 回归测试、NAS 部署验证、竞技场测试 | 代码开发 |

### FFL 团队内部角色

| 角色 | 职责 |
|------|------|
| **PM** | 工单认领、任务分配、进度跟踪、质量把关、与 dw 沟通 |
| **后端开发** | 网关、编译器、安全闸门、API 接口的 bug 修复和性能优化 |
| **前端开发** | WebUI 改进、移动端兼容、XSS 加固、UI/UX 优化 |
| **测试工程师** | 自动化测试编写、测试矩阵维护、回归测试、bug 复现 |
| **审查员 (Reviewer)** | 代码审查、安全审计、质量把关（FFL 内部初审） |

## 二、仓库结构

### 仓库关系

```
AutoFlow (主仓库，稳定版，给用户用)
    ↑ dw 审查后合并 PR
    │
autoflow-dev (开发仓库，FFL 团队工作区)
    ├── main 分支 (同步自主仓库)
    ├── feature/* 分支 (新功能开发)
    ├── fix/* 分支 (bug 修复)
    ├── perf/* 分支 (性能优化)
    ├── security/* 分支 (安全加固)
    └── test/* 分支 (测试改进)
```

### 分支命名规范

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feature/` | 新功能开发 | `feature/token-stats` |
| `fix/` | bug 修复 | `fix/gateway-429-retry` |
| `perf/` | 性能优化 | `perf/async-gateway` |
| `security/` | 安全加固 | `security/xss-escape` |
| `test/` | 测试改进 | `test/gateway-matrix` |
| `docs/` | 文档更新 | `docs/api-reference` |
| `chore/` | 杂项（构建、依赖等） | `chore/docker-non-root` |

### 提交信息规范（约定式提交）

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type 类型**：

| Type | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | bug 修复 |
| `perf` | 性能优化 |
| `security` | 安全加固 |
| `test` | 测试相关 |
| `docs` | 文档相关 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构（既不修复 bug 也不添加功能） |
| `chore` | 构建过程或辅助工具的变动 |
| `ci` | CI/CD 相关 |

**示例**：
```
fix(gateway): 修复 429 重试时未切换渠道的问题

- 添加渠道失败计数
- 连续失败 3 次自动切换到备用渠道
- 添加单元测试覆盖重试逻辑

Closes #123
```

## 三、工单流程

### 工单生命周期

```
dw 开工单
    ↓
FFL PM 认领 + 评估工时
    ↓
分配给开发者
    ↓
在 autoflow-dev 仓库开发 (feature/fix 分支)
    ↓
编写自动化测试
    ↓
FFL Reviewer 初审
    ↓
提交 PR 到 AutoFlow 主仓库
    ↓
dw 代码审查
    ├── 通过 → 合并到 master
    └── 不通过 → 返回修改 (回到开发阶段)
    ↓
wb2 回归测试
    ↓
dw 发布版本 (打 tag)
```

### 工单状态

| 状态 | 说明 |
|------|------|
| `待认领` | dw 已创建，FFL PM 尚未认领 |
| `已认领` | FFL PM 已认领，正在评估和分配 |
| `进行中` | 开发者正在开发 |
| `待审查` | 开发完成，FFL Reviewer 初审中 |
| `已提交PR` | 已提交 PR 到主仓库，等待 dw 审查 |
| `需修改` | dw 审查不通过，需要修改 |
| `已合并` | 已合并到 master |
| `已关闭` | 工单关闭（完成或取消） |

## 四、代码审查标准

### dw 审查清单（合并前必须通过）

- [ ] **安全性**：无 SQL 注入、XSS、命令注入、路径遍历等漏洞
- [ ] **密钥安全**：无硬编码 API Key、密码、Token
- [ ] **内网 IP 过滤**：无内网 IP 入库（P-2 门禁）
- [ ] **API Key 校验**：过期校验 fail-close（不是 fail-open）
- [ ] **测试覆盖**：核心逻辑有单元测试
- [ ] **代码质量**：无明显 bug、逻辑清晰、命名规范
- [ ] **文档**：公共 API 有文档注释
- [ ] **兼容性**：不破坏现有功能（向后兼容）
- [ ] **性能**：无明显性能退化（N+1 查询、阻塞调用等）

### FFL Reviewer 初审清单（提交 PR 前）

- [ ] 代码符合项目风格规范
- [ ] 无明显逻辑错误
- [ ] 测试用例覆盖主要场景
- [ ] 提交信息符合约定式提交规范
- [ ] 分支命名符合规范
- [ ] 无调试代码（console.log、print 等）
- [ ] 无注释掉的代码块

## 五、FFL 团队边界

### ✅ 可以做的

- bug 修复（网关、前端、测试、文档）
- 自动化测试编写和改进
- 性能优化（异步化、缓存、查询优化）
- 安全加固（XSS、注入、容器安全、依赖更新）
- 前端改进（UI/UX、移动端兼容、无障碍）
- 文档完善（API 文档、用户手册、开发指南）
- 代码重构（不改变外部行为的内部重构）
- 构建/部署改进（Docker、CI/CD、依赖管理）

### ❌ 不可以做的（需要 dw 批准）

- 架构变更（Pro 版架构、编译器核心、安全闸门）
- 新功能开发（需要 dw 开工单）
- 数据库 schema 变更
- API 接口变更（新增/修改/删除接口）
- 配置文件格式变更
- 版本发布（打 tag、发布 Release）
- 直接合并到 master（必须通过 PR + dw 审查）

### ⚠️ 需要先讨论的

- 大型重构（影响多个模块）
- 第三方依赖新增/升级
- 性能优化方案（可能影响稳定性）
- 安全方案设计（认证、授权、加密）

## 六、沟通机制

### 定期同步

| 频率 | 参与人 | 内容 | 方式 |
|------|--------|------|------|
| 每周一次 | dw + FFL PM | 本周完成、下周计划、阻塞问题 | 微信/飞书语音（15 分钟） |
| 每天一次 | FFL PM | 进度日报（可选） | 微信消息 |
| 紧急情况 | dw + FFL PM | 阻塞问题、紧急 bug | 微信即时沟通 |

### 沟通渠道

| 渠道 | 用途 |
|------|------|
| **GitHub PR** | 代码审查、技术讨论 |
| **GitHub Issue** | bug 报告、功能建议 |
| **微信** | 日常沟通、进度同步、紧急问题 |
| **工单文档** | 正式需求、验收标准 |

### 升级机制

如果 FFL 团队遇到以下情况，必须立即升级给 dw：
1. 发现严重安全漏洞
2. 架构层面的问题无法解决
3. 工单需求不明确，需要澄清
4. 预估工时超过原计划 50%
5. 需要做架构决策
6. 发现主仓库有严重 bug 需要紧急修复

## 七、版本发布

### 发布节奏

| 类型 | 频率 | 说明 |
|------|------|------|
| 小版本 (v1.x.y) | 每周 1-2 次 | bug 修复、小改进 |
| 大版本 (v1.x.0) | 每月 1 次 | 新功能、架构改进 |
| 紧急修复 | 随时 | 严重安全漏洞、数据丢失 bug |

### 发布流程

1. dw 决定发布内容和版本号
2. wb2 完成回归测试（NAS 部署验证）
3. dw 合并所有待发布 PR 到 master
4. dw 打 tag（`v1.x.y`）
5. dw 编写 Release Notes
6. 发布到 GitHub Release
7. 通知用户更新

### FFL 团队不参与发布

- FFL 团队不打 tag、不发布 Release
- FFL 团队只负责开发和提交 PR
- 发布权完全在 dw 手中
